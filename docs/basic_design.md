# 基本設計書：Mask & Unmask (MVP)

本基本設計書は、[要件定義書](./requirements.md)に基づき、システムのアーキテクチャ、コンポーネント構成、データ構造、およびコアアルゴリズムを定義します。

---

## 1. システム構成 & アーキテクチャ

本システムは、完全にWebブラウザ内で完結するフロントエンドアプリケーション（SPA）です。外部API通信やバックエンドDBは使用しません。

```mermaid
graph TD
    subgraph Browser["ユーザーブラウザ (ローカル完結)"]
        UI[UIコンポーネント層] <-->|State / Event| Controller[アプリ状態管理コントローラー]
        Controller <-->|Read / Write| Storage[(sessionStorage)]
        Controller -->|Validate Schema| SchemaValidator[JSONスキーマ検証器]
        Controller -->|Text Scan / Replace| MaskEngine[仮名化・復元エンジン]
        UI -->|File IO| LocalFile[ローカル JSON ファイル (エクスポート/インポート)]
    end
    Cloudflare[Cloudflare Pages (静的ホスティング)] -.->|HTTPS / アセット配信 (初回ロードのみ)| Browser
```

### アーキテクチャ制約
* **完全なスタティック配信:** 全てのアセット（HTML/JS/CSS/フォント）はホスティングサーバー（Cloudflare Pages）から初回ロード時に取得し、以降は一切の追加アセットを外部から取得しません。
* **外部アセット排除:** Google Fontsや外部CDNなどは利用せず、すべてローカルアセットとして同梱してビルドします。

## 3. データ構造 & 状態管理設計

### 3.1. 置換マップの型定義 (`MappingItem`)
```typescript
interface MappingItem {
  tag: string;       // 固有タグ例: "[CN_EMAIL_0001]"
  original: string;  // 元の機密テキスト
  category: "APIKEY" | "IPV4" | "IPV6" | "EMAIL" | "PHONE" | "CUSTOM";
  source: "AUTO" | "CUSTOM" | "IMPORT"; // マップアイテムの由来
}

type SubstitutionMap = MappingItem[];
```
* **注意:** インポート・エクスポートするJSONには `source` は含めず（JSONスキーマを要件定義書に準拠させるため）、インポート時に `source: "IMPORT"`、カスタム登録時に `source: "CUSTOM"`、自動検出時に `source: "AUTO"` をアプリケーション側で付与して管理します。

### 3.2. 原子的なアプリ状態永続化エンベロープ
リロード時のデータ消失を防ぐため、状態を単一のエンベロープオブジェクトに統合し、単一のキーで `sessionStorage` に永続化することで、書き込み処理の原子性（オール・オア・ナッシング）を保証します。

#### 型定義
```typescript
interface PersistedAppState {
  version: number;     // 状態構造のスキーマバージョン (初期値: 1)
  maskInput: string;   // 仮名化（Mask）入力テキスト
  unmaskInput: string; // 復元（Unmask）入力テキスト
  substitutionMap: MappingItem[]; // 置換マップの配列データ
  detectionToggles: Record<string, boolean>; // 各自動検出カテゴリのトグルON/OFF状態
  activeTab: "mask" | "unmask"; // 現在アクティブなタブ
}
```

#### 同期 & 例外処理ルール
* **キー名:** `cn_app_state`
* **書き込みフロー:**
  1. アプリ状態（React State）の更新時、最新の値を `PersistedAppState` にシリアライズ。
  2. `sessionStorage.setItem('cn_app_state', JSON.stringify(envelope))` を実行（`QuotaExceededError` の発生に備え `try-catch` を適用）。
  3. 書き込みが成功した場合のみ、React State の変更を確定する。書き込みに失敗した場合はロールバックし、画面上に「ブラウザの保存領域が不足しています。不要なマップを削除するかテキストをクリアしてください」という警告メッセージを表示する。
* **初期読み込み & 互換性チェック:**
  * アプリ起動時に `cn_app_state` をパース。
  * `SyntaxError` が発生した場合、または読み込んだオブジェクトの `version` が最新（`1`）と異なる、もしくは必須フィールドが不足している場合は、互換性なしと判断して `removeItem('cn_app_state')` を実行し、デフォルト値で状態を完全に初期化します。

## 4. コアアルゴリズム設計

### 4.1. 位置（インデックス）ベースの仮名化 (Mask) 処理

単純な一括置換（`replaceAll`）による誤置換やテキストの内部破壊を防ぐため、検出した位置情報に基づくスライシング置換を適用します。また、入力変更検知時には500msのdebounceを介して実行します。

#### データモデル
```typescript
interface DetectionMatch {
  start: number;       // 入力テキスト内の開始インデックス
  end: number;         // 入力テキスト内の終了インデックス
  original: string;    // マッチした文字列
  category: "APIKEY" | "IPV4" | "IPV6" | "EMAIL" | "PHONE" | "CUSTOM";
  tag: string;         // 割り当てられた、または割り当てる予定のタグ名
  source: "AUTO" | "CUSTOM" | "IMPORT"; // 候補の由来
}
```

#### 抽出用の共通正規表現
既存タグの検出、およびUnmask時のタグ抽出には、以下の共通正規表現を使用します（大文字小文字不問のため `i` フラグを適用）。
```typescript
const CN_TAG_REGEX = /\[\s*CN\s*_\s*(APIKEY|IPV4|IPV6|EMAIL|PHONE|CUSTOM)\s*_\s*(\d{4})\s*\]/gi;
```

> [!IMPORTANT]
> `CN_TAG_REGEX` には `g` フラグが含まれるため、同じRegExpインスタンスで `test()` や `exec()` などのスキャンを繰り返すと、マッチの進行に応じて内部の `lastIndex` 状態が変動します。
> 実装時は、スキャン実行ごとに新しいRegExpインスタンスを生成するか、`String.prototype.matchAll(CN_TAG_REGEX)` を用いることで、`lastIndex` の残存によるマッチ漏れや無限ループのバグを確実に防止します。

#### 処理フロー
1. **一時除外リスト (`ExcludeList`) の管理:**
   * 入力テキストが前回実行時の値から変更された場合、一時除外リスト（`Set<string>`）をクリアする。
2. **既存タグの検出・警告表示:**
   * 入力テキスト内に、`CN_TAG_REGEX` にマッチする既存の仮名化済みタグ文字列が含まれているかスキャン。
   * 検出された場合は置換処理をスキップし、UI上に警告メッセージを表示する。
3. **全候補 (Matches) の一括収集:**
   * 以下のソースからマッチ候補 `DetectionMatch` を配列に収集する：
     * **AUTO:** トグルがONの自動検出パターン（正規表現）でスキャンした結果。
     * **CUSTOM / IMPORT:** すでに `substitutionMap` 内に `source: "CUSTOM"` または `source: "IMPORT"` として登録されている `original` の値と入力テキストが一致した箇所。
4. **一時除外リストの適用:**
   * 収集した候補のうち、`original` が「一時除外リスト」に含まれる候補を配列から取り除く。
5. **一括競合解決 (Conflict Resolution):**
   * 収集された候補群に対し、重複や交差を解決するために以下の優先順位（1〜5の滝流れ）に従って決定的にフィルタリングを行う：
     * **ルール1（来歴の優先）:** 位置が重複または交差する場合、`CUSTOM` / `IMPORT` (手動またはインポート値) を `AUTO` (自動検出値) より優先する。
     * **ルール2（最長一致優先）:** 同じ開始位置、または重なり合う範囲のマッチがある場合、最も文字列長が長いマッチ（`end - start` の最大値）を優先する。
     * **ルール3（カテゴリ優先）:** ルール1・2で解決しない重なりの場合は、`APIKEY` ➔ `EMAIL` ➔ `PHONE` ➔ `IPV6` ➔ `IPV4` の順に優先適用する。
     * **ルール4（開始位置の優先）:** それでも重複が残る場合は、開始位置 `start` が小さい（左側にある）候補を優先する（タイブレーク）。
     * **ルール5（タグ辞書順）:** 開始位置・長さともに同一で交差する場合は、割り当てられているタグ名 `tag` の辞書順（昇順）を優先する（決定性タイブレーク）。
6. **タグ採番と衝突回避:**
   * 各カテゴリごとに `0001` から始まる4桁の連番を生成。
   * すでに同一の `original` がマップにある場合はそのタグを再利用。
   * 採番の際、既存のマップ（インポートやカスタム登録済みタグ）と番号の衝突が発生しないよう、既存カテゴリタグの最大連番を上回る未使用番号を割り当てる。
   * 採番が `9999` に達した場合、仮名化処理を中断して「[CATEGORY]のタグ上限に達しました」というエラーメッセージをトーストで表示する。
7. **スライシングによるテキストの再構築:**
   * 競合解決された非重複マッチを `start` の昇順でソートする。
   * 隣り合うマッチについて、`start` が前の `end` 以上であることを検証（非重複アサーション）。
   * 入力テキストを非置換領域と置換後のタグ文字列にスライスして交互に連結し、最終テキストを構築する。
     ```typescript
     let result = "";
     let lastIndex = 0;
     for (const match of sortedMatches) {
       result += inputText.slice(lastIndex, match.start) + match.tag;
       lastIndex = match.end;
     }
     result += inputText.slice(lastIndex);
     ```

### 4.2. マップのライフサイクルルール
* **トグルOFF時:** トグルがOFFになったカテゴリに属し、かつ `source: "AUTO"` であるマップアイテムを即時削除する。
* **入力テキストからの消失時:** 入力テキストの変更に伴い、検出されなくなった `source: "AUTO"` のマップアイテムは即時削除する。
* **手動登録・インポート保護:** `source: "CUSTOM"` および `source: "IMPORT"` のアイテムは、入力テキスト内に含まれなくなっても自動削除されず保持される。

### 4.3. 復元 (Unmask) 処理アルゴリズム

復元された元の値の中に他のタグ文字列が含まれていた場合の二重置換（データ破損）を防ぐため、Mask処理と同様に位置（インデックス）ベースで一度だけテキスト出力を再構築します。
※画面幅（PC/モバイル表示）の変更によって復元データが消失する不整合を防ぐため、Unmask処理エンジンに渡す置換マップデータは画面幅によって制限せず、PC/モバイル共通とします。

#### 処理フロー
1. **タグ候補の位置情報付き抽出と標準化 (Normalization):**
   * 入力テキストから `CN_TAG_REGEX` (新しい RegExp インスタンスまたは `matchAll`) を用いて、テキスト内のすべてのタグ候補の `start`、`end`、およびマッチした表記揺れ状態のタグ文字列を抽出。
   * 抽出した各タグ文字列の空白を除去し大文字に統一して、対応する「標準化タグ表記」（例: `[ cn_custom _ 0001 ]` ➔ `[CN_CUSTOM_0001]`）を作成。
2. **置換マップとの照合:**
   * 各標準化タグが、置換マップ（`PersistedAppState` 内のデータ）に存在するかを確認。
   * 存在する場合、その `original` の値と対応カテゴリを紐付けた復元マッチ候補を作成。
3. **一括競合解決:**
   * 抽出したタグ候補に重なりがある場合は、Mask時と同様の優先度（最長一致、開始位置 `start` 昇順）に従って一括競合解決し、非重複の復元リストを確定する。
4. **位置ベースのスライシングによる復元テキストの再構築:**
   * 確定した復元リストを開始位置 `start` の昇順でソートする。
   * 入力テキストを非置換領域と、マップから取得した `original` のテキストスライスに分解し、一度だけ結合して最終テキストを再構築する（復元された値が以降の走査で再置換されることを防ぐ）。
5. **復元状況の集計 (`RestoreStatus`):**
   * **成功件数 (`restoreCount`):** 上記ステップで正常に復元（置換）が行われたタグのユニーク件数。
   * **未復元タグ一覧 (`unrestoredTags`):** 入力テキスト中から抽出されたが、置換マップに存在しなかった標準化タグ名のリスト。

## 5. インポート / エクスポート & バリデーション設計

### 5.1. JSONスキーマ検証 (JSON Schema)
[要件定義のスキーマ定義](./requirements.md#5-置換マップのjsonスキーマ定義)に準拠した検証をインポート時に実行します。
* `mappings` プロパティの配列に `"maxItems": 1000` の上限制約を適用。
* `properties` 内の各タイプ指定はすべて小文字（`object`、`string`、`array`）とする。
* ルートおよび `mappings` 配列内のオブジェクトスキーマに `"additionalProperties": false` を定義し、未知のプロパティを却下する。

### 5.2. アプリケーション層での追加検証 (一貫性バリデーション)
JSON Schemaによる検証成功後、以下の検証を実行します。不一致があった場合はインポート全体を中断します。
* 各マッピングデータの `tag` のカテゴリ名部分（例: `[CN_EMAIL_0001]` ➔ `EMAIL`）を抽出し、`category` プロパティの値（例: `EMAIL`）と一致しているか検証する。不一致の場合はエラー。

### 5.3. トランザクション的インポートフロー
データの不整合や部分適用を防ぐため、インポートは検証と確定処理をメモリ上で分離します。

```
[JSON ファイル選択]
      │
      ▼
1. サイズチェック (500KB 超はエラー表示して中断)
      │
      ▼
2. テキスト読み込み (FileReader: UTF-8 強制)
      │
      ▼
3. JSON パース (構文エラーはエラー表示して中断)
      │
      ▼
4. JSON Schema バリデーション (スキーマ不一致はエラー表示して中断)
      │
      ▼
5. アプリケーション層一貫性検証 (タグとカテゴリの不一致はエラー表示して中断)
      │
      ▼
6. 競合解決 & 上限チェック (マージ衝突解決、1000件超過チェック)
      │
      ▼
7. プレビューダイアログ表示 (インポート予定のタグ数や競合処理要約を表示)
      │
      ▼
[ユーザー確定操作]
      │
      ▼
8. React State & sessionStorage の一括更新 (トランザクション確定)
```

#### 競合解決ルール (Conflict Resolution)
* **同一のタグで異なる original:** インポート側のタグを、既存のマップと重複しない新しい連番に自動リナンバリングしてマージ登録する。
* **異なるタグで同じ original:** 既存のタグを優先し、インポート側のタグは統合して破棄する。
* **タグと category の不一致:** インポート前のバリデーションで却下されるため、競合処理レイヤーでは考慮しない。
* **マージ後の上限超過:** マージ後の合計件数が1000件を超える場合、インポート処理全体を中断し、超過エラーを表示する。

#### エクスポート仕様
* ファイル名: `circlemaps_YYYYMMDDHHMMSS.json`（出力時のタイムスタンプ付与）
* MIMEタイプ: `application/json`

## 6. セキュリティ & 技術仕様

### 6.1. コンテンツセキュリティポリシー (CSP)
サーバー配信設定にて以下のCSPヘッダーを適用し、外部接続およびスクリプトの実行コンテキストを制御します。

```http
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'none'; font-src 'self'; object-src 'none'; frame-ancestors 'none'; form-action 'none'; base-uri 'none';
```
* `connect-src 'none'`: アプリ起動後、ブラウザからFetch、XHR、WebSocketなどを利用した外部サーバーへのいかなるネットワークリクエストの送信も遮断・拒否します。

### 6.2. クリップボード・フォールバック
`Clipboard API` によるコピー処理がブラウザのセキュリティ制限（非HTTPS環境、または権限拒否）によって失敗した場合、以下のフォールバックを行います。
* コピー対象の `<textarea>` 要素のテキストを全選択（`select()`）したフォーカス状態にする。
* UI上に「コピーに失敗しました。選択範囲を手動（Ctrl+C 等）でコピーしてください」というトースト通知を表示する。

### 6.3. sessionStorage の容量保護
`sessionStorage` への書き込み処理全体を `try-catch` で囲み、ブラウザ上限容量に達して `QuotaExceededError` が発生した場合は、変更前の React State を維持（ロールバック）し、画面上に「ブラウザの保存領域が不足しています。不要なマップを削除するかテキストをクリアしてください」という警告メッセージを表示します。

### 6.4. 性能検証方法（パフォーマンス）
非機能要件の100KB処理性能目標（p95で50ms以内）を開発環境および検証環境でテストするため、以下の測定プログラムを開発用テストスイートに組み込みます。

1. **固定テストデータ:** 100KB（約5万字）で、APIキー・メールアドレス・IPアドレス・電話番号の機密データパターンがそれぞれ20箇所以上埋め込まれたダミーテキストを用意。
2. **ウォームアップ:** JSエンジン（JIT）の最適化を促すため、事前に変換処理を10回空実行。
3. **複数回測定:** `performance.now()` を用いて、変換処理を100回連続で計測。
4. **p95の判定:** 測定された100個の所要時間を昇順にソートし、95番目の値（95パーセンタイル値）を抽出。これが50ms以下であることをアサーションし、結果をコンソールに出力する。
5. FCP (1.5秒以下)・LCP (2.0秒以下) の検証は、Chrome DevTools の Lighthouse プロファイラーを用いて検証環境で別途測定する。
