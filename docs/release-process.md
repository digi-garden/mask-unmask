# Mask & Unmask リリース判定・復旧運用手順

## 目的と判断基準

本書はMask & Unmask固有の配布・検証・障害時の復旧手順を記録するものです。リリース可否の判定基準は、digi-garden共通規約 v1.1（`digi-garden/brand-assets`、固定コミット `31bf40e921661c9c8e7b246434b349ad71c7c578`）の `templates/release/product-release-checklist.md` を**唯一のマスターチェックリスト**として使用します。本書のチェック項目でGate Aの要件を代替・緩和しません。

本プロダクトは公開Web版であり、README記載の公開URLは `https://circle-note.com/mask-unmask/` です。現在のホスティングサービス、デプロイ自動化、公開停止方法、復元機能の詳細は本書作成時点で**未検証**です。必ず運用担当が確認した実際のサービス・画面に合わせてリリース記録へ入力してください。未確認のまま公開操作・ロールバック操作を実施しないでください。

## 通常リリース（実行順）

1. **変更凍結と識別**：対象PR、mainのコミットSHA、製品バージョン、ソースとビルド成果物の対応、デプロイ先のアカウント・プロジェクト・環境を記録する。未マージのPRを公開済みと誤記しない。
2. **Gate A判定**：共通マスターチェックリストの全項目を `PASS / FAIL / N/A / NOT_RUN` で評価し、証跡URLを残す。未知の重大リスクやGate A FAILがあれば公開しない。
3. **事前テスト**：対象SHAのCI（type-check、unit、perf、build、Playwright E2E）を確認する。CSP/HTTPヘッダー、プライバシー、法務ページ、OSS表示、プライベート脆弱性報告導線を検証する。
4. **バックアップ・切り戻し準備**：直前に**正常稼働が確認済み**のデプロイID、日時、成果物、対応SHA、切り戻し担当者と権限を記録する。ホスティングのデプロイ履歴・再デプロイ／ロールバック機能を実際に確認する。機能がない場合は再配布可能な旧成果物と操作手順を確保する。
5. **公開操作**：運用担当が承認された経路で対象成果物をデプロイし、公開実施時刻、デプロイID、操作者を記録する。本書やCIの存在だけでは自動公開を許可しない。
6. **公開後検証**：デプロイが反映されたことを識別したうえで `npm run verify:production`（該当スクリプトを含む変更がマージ済みの場合）を実行し、DevToolsで架空データによるMask/Unmask・クリア・通信確認、直接URLアクセス、法務リンク、レスポンスCSPを検証する。
7. **最終判定記録**：共通マスターの最終判定、未対応課題、例外、追加対応と公開後確認の結果を `docs/release-record-template.md` を複製した**リリース単位の証跡**へ記録する。記録ファイルには秘密情報や実際の機密入力データを入れない。

## 障害・公開停止・切り戻し

- **判断トリガー**：機密情報が外部送信される疑い、復元データの破損、CSP欠落、重大法令表示の欠陥、主要動線停止など。重大な安全性問題はGate Aの公開停止条件として扱う。
- **初動**：公開後の確認を中断し、事象・影響・発生日時・最新正常版を記録する。必要に応じホスティング管理画面等の**実在が確認された**公開停止機能を使う。稼働中の問題に対してデプロイ操作を試行錯誤しない。
- **切り戻し**：事前記録した旧正常デプロイを、ホストがサポートするロールバック／再デプロイ機能で選択する。旧版が事故の原因を含む場合は戻さず公開停止等を検討する。実施者と対象IDをダブルチェックする。
- **復旧検証**：対象URLが旧正常版に戻ったことを、デプロイ識別情報・ブラウザ動作・本番ヘッダー・主要動線で確認する。キャッシュやCDNの旧新混在も確認する。
- **事後対応**：原因、影響範囲、検出方法、実施操作、復旧までの時間、再発防止策、ユーザー通知・GitHub Advisoryの要否を記録する。

**注意**：Mask & Unmaskは`sessionStorage`に入力や置換マップを一時保持します。Webアセットの切り戻しは利用者のブラウザ内データを復元しません。古いJSと新しい保存形式の互換性、およびブラウザセッションの残存をテストしてください。利用者の機密入力をサーバーへ回収して「復元」する運用は禁止します。

## 定期訓練と変更時の確認

- デプロイ経路・ホスト設定・DNS・キャッシュ戦略・ストレージ形式が変わるたび、実際の切り戻し経路と権限を再確認する。
- 本番切り戻し訓練が不適切な場合はステージング等の安全な環境で実施し、**本番切り戻し未検証**と明記する。手順書を書いたことを復旧能力の実証として扱わない。
- 緊急修正時も共通規約のGate A判断を省略せず、未実施テストの理由・影響・残余リスクを記録する。
